## 1. Behavioral spec

**Symptom being fixed** (plan lines 22–24, 30–31): the exporter flattens all
four `building_panel` modes plus the `ConstructPreview` modal into ONE
superimposed snapshot the game never shows
(`tools/export_ui_layouts.py:168-212` — one `BuildingUI` construction + a
forced `_build_base_info` + a `ConstructPreview`, all merged into a single
`widgets` dict). Worse, mode-dependent geometry is recorded from `__init__`
before any mode builder runs: `action_btn` exports at its construction rect
`(panel_x+12, 0, panel_w-24, 36)` (`game/ui/building_ui.py:317-318`) even
though the game shows it at `y=150` in unlock mode
(`building_ui.py:478`) and at `y=view_h-120` in upgrade mode
(`building_ui.py:537-538`).

**Required behavior after UH-1:**

1. `data/ui/screen_defaults.json`'s `building_panel` entry gains a `views`
   object with **exactly five keys**: `unlock`, `construct`, `upgrade`,
   `base_info`, `preview` (D2, plan lines 42–46; goal, lines 79–82). Each
   view is `{widgets: {<id>: {rect, kind, label}}, mock_note}` — the same
   widget-entry shape as today (`data/schemas/screen_defaults.schema.json:16-47`),
   holding only the widgets the game actually draws in that mode, with that
   mode's real geometry and labels.
2. **Per-view widget membership mirrors the game's mode branches**
   (`building_ui.py:663-704` hover dispatch, `:734-742` click dispatch,
   and the mode builders):
   - `unlock`: `panel`, `close_btn`, `action_btn` (rect from
     `_build_unlock`, `building_ui.py:478`).
   - `construct`: `panel`, `close_btn` only — construct cards are
     dynamic-count and deliberately un-id'd (`building_ui.py:499-502`, B3
     rule); the view's `mock_note` must say so.
   - `upgrade`: `panel`, `close_btn`, `action_btn` (rect from
     `_build_upgrade`, `building_ui.py:537-538`), `rename_dice_btn`
     (`building_ui.py:309-311`, drawn only in upgrade — `:679-682`).
   - `base_info`: `panel`, `close_btn`, `boss_btn`, `boss_close_btn`,
     `lightning_btn` (rebuilt per call in `_build_base_info`,
     `building_ui.py:579-588`; the existing exporter stand-in at
     `export_ui_layouts.py:193-197` moves here).
   - `preview`: the five `preview_*` ids from `ConstructPreview.__init__`
     (`building_ui.py:163-168`; `preview_cancel_btn` present iff
     `construct_show_cancel` — same conditional as today,
     `export_ui_layouts.py:199-207`).
3. **The top-level `widgets` key stays, for every screen, and for
   `building_panel` becomes the deterministic union of its views.** This is
   what makes "game side read of defaults is untouched — game never reads
   views" (plan lines 85–86) true *by construction*: the game reads
   `defaults[screen_id]["widgets"]` only as the known-id set for override
   validation (`game/ui/skinning.py:190-194`), and the current editor reads
   the same key (`editor/panels/viewport.py:144`, `:353-359`;
   `editor/panels/screen_details.py:340`). Both keep working unmodified;
   UH-2 teaches the editor to read `views`.
4. **The other 12 screens change shape not at all** — no `views` key, single
   implicit default view (plan lines 81–82; "no format churn"). Their bytes
   in the regenerated file may still shift only if unrelated defaults
   drifted — they should not; the regeneration diff must be confined to
   `building_panel`.
5. The committed `data/ui/screen_defaults.json` is regenerated by
   `py tools/export_ui_layouts.py` in the same commit as the code/schema
   change — the staleness test enforces byte-freshness
   (`tools/tests/test_ui_layout_export.py:24-39`).

## 2. Architecture plan

**Exporter (`tools/export_ui_layouts.py`).** Replace the single
`_build_building_panel` (lines 168–212) with five per-view builders plus a
union step, keeping the module's existing conventions (headless SDL dummy
at import, `_widget_entry`/`_widgets_from_ids` as the only
entry-construction path, `build_screen_defaults`'s fail-loud wrapper at
lines 268–278):

- **Fresh `BuildingUI` per view.** Each view builder constructs its own
  `BuildingUI(view_w, view_h, ui_balance)` so no state (e.g. `action_btn`'s
  rect/label, `_action_cost`) leaks between views — this is the determinism
  guarantee at the object level. Mode builders are invoked **directly**
  (never through `open_for_tile`, which needs real tiles/occupants — the
  existing `_build_base_info` stand-in precedent,
  `export_ui_layouts.py:189-197`), always real game code fed mock data,
  never monkeypatched game internals:
  - `unlock`: set `panel.selected_tiles = [tile]` with
    `tile = SimpleNamespace(col=?, row=?)` (fixed small ints), and call
    `panel._build_unlock(session)` where `session.tilemap` is a
    `SimpleNamespace` exposing the three callables `_build_unlock` reads
    (`building_ui.py:472-476`): `get_chunk_for_tile=lambda t: [t]`,
    `unlock_cost=lambda t: <fixed const>`, `can_unlock=lambda t: True`.
    Mock values go in the view's `mock_note`.
  - `construct`: **do not run `_build_construct`** — it populates only the
    un-id'd cards; the view emits the mode-independent subset with a
    `mock_note` naming the cards as `defaults.button_skin` territory.
  - `upgrade`: build a real building the way `ConstructPreview` already does
    in this exporter's path — `create(_MOCK_BUILDING_TYPE, 0, 0,
    buildings_balance, 0)` (`building_ui.py:128` precedent) — set
    `panel._selected`, `panel.selected_tiles`, `panel._session`,
    `panel._buildings_balance`, and call `panel._build_upgrade()`
    (`building_ui.py:531-542`). It needs `upgrade_gate(session.state, b,
    balance)` (`building_ui.py:548-549`): prefer a real, freshly-constructed
    run-state object if it constructs headlessly without a world; fall back
    to a `SimpleNamespace` carrying only the attributes `upgrade_gate`
    actually reads (executor: read `game/core/levelup.py::upgrade_gate` and
    pin them). Either way the gate outcome must be deterministic; record it
    in `mock_note`.
  - `base_info`: today's stand-in session block
    (`export_ui_layouts.py:189-197`) relocates here verbatim; add
    `boss_btn`/`boss_close_btn` from `panel.ids`.
  - `preview`: today's `ConstructPreview` block
    (`export_ui_layouts.py:199-207`) relocates here.
- **Union.** A module-level canonical view-order tuple (e.g.
  `_BP_VIEW_ORDER = ("unlock", "construct", "upgrade", "base_info",
  "preview")`), first-wins per widget id, produces the top-level `widgets`
  dict from the already-built view entries. First-wins over a fixed order is
  fully deterministic; which rect wins for `action_btn` is cosmetic (the
  union exists for the id set + legacy readers, not per-mode geometry).
- **Every widget entry — view or union — is produced by
  `_widgets_from_ids`/`_widget_entry`** (`export_ui_layouts.py:75-95`; the
  union copies references to view-built entries). This is a UH-4 contract —
  see §3.
- Output shape for `building_panel`:
  `{widgets: <union>, views: {...}, mock_note: <existing union note>}`;
  the other 12 screens' builders and output are untouched.

**Schema (`data/schemas/screen_defaults.schema.json`).** Hoist the
widget-entry subschema (current lines 16–47) into `$defs` under the key
**`widget`**, referenced via local `#/$defs/widget` from both places (local
`$defs` refs only — the 9A house rule, `data/CLAUDE.md` "Schema shape").
Add to the per-screen object an **optional** `views` property:
`additionalProperties:false`, `patternProperties` `^[a-z][a-z0-9_]*$` →
`{widgets: {patternProperties → #/$defs/widget}, mock_note}` with
`required: ["widgets"]` — i.e. a view body is shaped exactly like a screen
body. Top-level `widgets` stays `required`. Author the schema through
`dumps_deterministic` (house style); content regenerates through
`write_validated` (D-3 canonical form, `export_ui_layouts.py:299`).

**Determinism strategy (byte-idempotent, sha-measured like B3).** Same
mechanics that made B3 deterministic, now per view: fixed mock constants,
fresh objects per view, `layout_h` pinned font table (never live font
measurement — `game/ui/CLAUDE.md` "Layout heights"), sorted-keys 2-space
canonical dump. Measured by the existing two-independent-regenerations
byte-equality test (`tools/tests/test_ui_layout_export.py:41-53`) plus the
staleness diff (`:24-39`) — both work unmodified on the new shape since
they compare whole-file bytes. `tools/tests/test_layout_h_invariant.py:56-66`
also regenerates the exporter output under a +1px font perturbation and
covers the new shape for free. The executor's report states the sha256 of
two independent regenerations (measured claim).

**New tests** (extend `tools/tests/test_ui_layout_export.py`; plan lines
87–89): (a) `building_panel` has exactly the five view keys; (b) membership
pins — `action_btn` in `unlock` and `upgrade` with **different** rects,
`rename_dice_btn` only in `upgrade`, `lightning_btn` only in `base_info`,
`preview_*` only in `preview`, `panel`/`close_btn` in the four panel views;
(c) top-level `widgets` key-set == set-union of the view key-sets (pins the
game's validation id-set to the views); (d) no other screen carries a
`views` key. All run the exporter into a tempdir via
`export_main(data_root=..., output_dir=...)` — never against live `data/`
(the `test_ui_layout_export.py:30-34` pattern).

**Shared-file contract with UH-4** (UH-4 adds optional per-widget
`display_name`, authored as an exporter-side mapping — plan lines 123–133):
1. **Schema insertion point**: UH-4 adds `display_name` as an optional
   property inside the single **`$defs/widget`** node UH-1 creates —
   never into the inline per-screen or per-view widget subschemas (UH-1
   leaves exactly one widget-entry definition; UH-4 must not fork it). It
   then applies to union and view entries automatically.
2. **Exporter insertion point** — *amended by the orchestrator during Wave-1
   reconciliation; this supersedes the original choke-point instruction and
   matches `phase-uh-4-display-names.md` §3.* UH-4 **does NOT** inject at
   `_widget_entry`/`_widgets_from_ids` and does not change their signatures.
   Rationale (verified by the UH-4 planner): the builders and `_widget_entry`
   (`tools/export_ui_layouts.py:75-95`) never receive the screen id, so a
   per-screen id→name mapping cannot be resolved there without threading a
   new argument through every builder — which would collide head-on with
   UH-1's rewrite of those same builders.
   Instead UH-4 adds a `_DISPLAY_NAMES` mapping constant plus an
   `_apply_display_names` post-pass called once inside `build_screen_defaults`
   (UH-4 owns the region after `_MOCK_BUILDING_TYPE`, ~line 64, and the call
   site in `build_screen_defaults`). The post-pass annotates widgets
   **wherever a `widgets` mapping appears in a screen entry — both the
   top-level union and inside each view**.
   **Binding requirement on UH-1**: keep the key name `widgets` for the widget
   mapping at BOTH the top level and inside every view value (already the case
   per §2's `{widgets, mock_note}` view shape) — UH-4's post-pass walks that
   key name. UH-1 still routes all entry construction through
   `_widget_entry`/`_widgets_from_ids` for its own determinism reasons, but
   UH-4 stays entirely out of those functions and out of the `_build_*`
   builders, so the two diffs are textually disjoint.
3. **`data/ui/screen_defaults.json` is never merged by hand.** Any merge
   conflict between UH-1 and UH-4 (or anything else) is resolved by
   rebasing the code, then re-running `py tools/export_ui_layouts.py` and
   committing its output — the file is generated-but-committed and the
   exporter is deterministic (`data/CLAUDE.md` "UI screen data"; plan risk
   lines 177–179). Whichever of UH-1/UH-4 lands second rebases and
   regenerates.
4. UH-2 consumes this phase's shape read-only: view names come from
   `defaults["building_panel"]["views"].keys()`; screens without `views`
   render exactly as today.
