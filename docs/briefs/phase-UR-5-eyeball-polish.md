# Phase UR-5 — Eyeball / playtest polish

Source plan: `planning/UiResolutionPLAN.md` §"Phase UR-5" (lines 209-222), with
the conversion rule at §2 (lines 57-70), the deferred world zoom at §3
(lines 72-86) and the open risks at §5 (lines 226-249).

> **UR-5 cannot be fully closed by an agent.** Its exit criterion is a human
> eye (plan line 221-222: "GATE PASS **plus explicit user sign-off from a live
> playtest**"). An executing agent can land the mechanical checks in §1, triage
> and fix what they flag, and then **stop and hand the playtest script in §4 to
> the user**. Declaring UR-5 done without a signed-off playtest is out of
> scope. No new test coverage is expected beyond re-pinning what moves
> (plan line 219).

This is a **checklist + triage protocol**, not a task list: the file scope is
"whatever the playtest surfaces", and a brief cannot enumerate unknown fixes.
What it *can* do is enumerate the defect **classes** the conversion rule
predicts, say where each one lives, and make three of the four checkable
without a human.

## 1. Behavioral spec — the defect classes UR-2 predicts

UR-2 halves the surface (`data/display.json` 1280×720 → 640×360) and halves
every constant it judged to be 1280-scale, while deliberately leaving the
constants it judged already-640-scale alone (`data/ui/fonts.json`'s 7 presets,
the 18×18 HUD icons — plan lines 63-67). Four things go wrong when that
judgement is imperfect. Each is stated as: what the defect is → where to look
→ whether a machine can find it.

### (a) Odd-pixel rounding — an odd 1280-scale constant was halved

Halving an odd number loses half a pixel. Two failure modes: the fix rounded
(the element is now 1px off its neighbour, so a border, an inset or a stacked
row no longer aligns), or it truncated toward zero (a 1px-tall separator
becomes 0px and vanishes).

Known odd constants that UR-2 must have touched, all **verified** by reading:

| Site | Value | ÷2 |
|---|---|---|
| `game/ui/pause.py:33` `_BTN_W, _BTN_H, _GAP` | `240, 46, 12` | `120, 23, 6` |
| `game/ui/hud.py:197` / `:284` `_xp_bar.rect` | `(…, 110, 9)` | `9 → 4.5` |
| `data/ui/screens/hud.json` `love_panel` | `[12, 12, 107, 39]` | `53.5 × 19.5` |
| `data/ui/screens/hud.json` `readout_panel` | `[12, 46, 107, 57]` | `53.5 × 28.5` |
| `game/ui/highscores.py:69` `_HEADER_GAP` | `30` | `15` |
| `game/ui/credits.py:41-42` `_LINE_H, _SPACER_H` | `30, 14` | `15, 7` |
| `game/ui/hud.py:497` separator `HudRect((bx, by - 2, bw, 1))` | height `1` | `0` if halved |

That last row is the truncation case in the flesh: a `width=1` / height-1
primitive must **stay 1** — it is already a 640-scale hairline (the thinnest
line that exists), not a 1280-scale measurement. Same for every `width=1` /
`width=2` border argument in `game/ui/widgets.py:200,267,375` and every
`border_radius=3` — these are chrome, bucket "leave it" per plan line 64-67.

**Mechanical check (automatable).** The whole layout is already exported to a
single artifact: `data/ui/screen_defaults.json`, regenerated by
`tools/export_ui_layouts.py` (`build_screen_defaults`, line 518; it reads the
resolution from `display.json` via `_logical_resolution`, line 200-205, so it
tracks the flip for free). Diff the pre-UR-2 committed copy against the
post-UR-2 one and flag every widget field where `new != old / 2` exactly:

```bash
git show <pre-UR-2-rev>:data/ui/screen_defaults.json > /tmp/before.json
# then, for each screen/widget/rect index: old % 2 != 0  ->  report
```

Every hit is a *candidate*, not a bug — a hairline that correctly stayed 1 will
be flagged too. This is a triage worklist, not an assertion, so it belongs in
the scratchpad as a throwaway script, **not** as a committed test.

### (b) Text overflowing a halved container

Font presets did **not** halve (plan line 64-65, `data/ui/fonts.json`: `sm 9`,
`md 11`, `lg 13`, `xl 18`, `xxl 26` — **verified**, all still at their
prototype values). Containers did. So every label that used to have slack has
half the slack, and any label that was already close now clips.

Where to look:
- **Button labels.** `widgets.Button.submit` (`game/ui/widgets.py:349-379`)
  centres the label and does **no fitting or truncation** — it draws the string
  at `x + w // 2` whatever the width. A too-long label overhangs both edges
  silently. The longest shipped labels are `main_menu.py:52` `_ITEMS`
  (`START NEW GAME`, `HIGH SCORES`) at `_BTN_W = 320 → 160` (`main_menu.py:76`)
  and `pause.py:22` `_ITEMS` at `240 → 120` (`pause.py:33`).
- **Wrapped body text.** `widgets.wrap_text` (`widgets.py:152-167`) is the only
  fitting primitive and its docstring is explicit: *"A word longer than the
  line is not broken (it just overhangs)"*. Its two callers are
  `levelup.py:165` (option explanation, `w - 16`, `max_lines=4`) and
  `tutorial_message.py:93`. A halved box plus an unchanged font is exactly the
  case where a single long word now overhangs.
- **Self-sizing tooltips are safe** — `building_ui.py:1516,1534` and
  `hud.py:565` size their panel from `text_size(...) + padding`, so they grow
  instead of clipping. They may now overflow the *screen edge* instead: check
  a tooltip opened near the right/bottom border.
- **Row heights vs. line height.** `highscores.py:68` `_ROW_H = 28 → 14`
  against `sm`'s 9px glyphs plus `layout_h`; `game_log.py:29` `_LINE_STEP = 12`
  (if UR-2 halved it → 6, below the font). `credits.py:41` `_LINE_H = 30 → 15`.

**Mechanical check (partly automatable).** Every screen exposes its named
widgets as an `ids` dict `{name: (kind, widget)}` (the B2 contract,
`game/ui/skinning.py`), and a `Button` carries both `.label` and `.font_key`
(`widgets.py:291-300`). A test can walk each screen's `ids`, and for every
`kind == "button"` assert
`widgets.text_size(label, font_key)[0] <= rect_w - 4`. That covers **static**
labels only — dynamic ones (building display names, player names, custom
names, high-score rows) are eyeball-only and belong in §4's playtest.

### (c) Click targets under a usable minimum

Plan §5 (lines 231-235): *"Every button halves in logical pixels. `SCALED`
means they occupy the same physical screen area, so this should be neutral —
but sub-pixel rounding in the mouse remap at non-integer monitor scales could
make edges of small controls unreliable. Worth a deliberate check in UR-5."*

The concrete instances (**verified**): `pause.py:33` `_BTN_H = 46 → 23`;
`data/ui/screens/hud.json` `btn_pause` `[1174, 12, 90, 30] → 45×15`;
the speed pills and `btn_drag_select` (90×28 → 45×14, `game/ui/CLAUDE.md`'s
drag-selection section); `main_menu.py:76` `_BTN_H = 52 → 26` and
`_GEAR_W` beside it (`main_menu.py:105`, the smallest menu control there is).

Two mechanisms make this worse than the raw arithmetic:
1. **The pixel-perfect skin hit test.** `widgets.Button._surface_hit`
   (`widgets.py:302-311`) delegates to the host-injected
   `assets.hit_opaque` seam (`set_skin_hit_test`, `widgets.py:29-34`) and
   queries the canonical `("idle", 0)` silhouette at `dest_size = (w, h)`.
   With `w, h` halved, the nine-slice is sampled at half resolution — a skin
   whose border pixels are semi-transparent can lose its outermost clickable
   ring entirely. Every one of the `hud.json` / `settings.json` /
   `main_menu.json` buttons carries a `skin` key (`ui_button_panel`,
   `ui_button_pill`, `ui_button_end_turn`, `ui_button_pause`), so this is the
   normal path, not an edge case.
2. **`SCALED` is only an integer multiple on standard 16:9 sizes** — plan §5
   lines 236-239: exactly 2× at 1280×720, 3× at 1920×1080, 4× at 2560×1440,
   *"but not on 1366×768. Pixel art will resample unevenly there. Not solved
   by this plan; note it if it bites."* A 14px-tall pill under a 1.9-ish
   remap is where an unreliable edge shows up first. **Treat a click-target
   failure that only reproduces on a non-integer-multiple resolution as a
   NOTE, not a UR-5 fix** — it is §5's acknowledged out-of-scope item.

**Mechanical check (automatable, and this one should be committed).** Walk
`data/ui/screen_defaults.json` (or each screen's `ids`) and assert that every
`kind == "button"` rect has `w >= MIN` and `h >= MIN`.

> **Open question for the user/orchestrator: what is MIN?** Proposed default
> **12 logical px** as a hard failure (≈24 physical px at the 2× reference
> monitor, the conventional minimum pointer target) with anything **under 16**
> reported as an eyeball candidate. This number is *inferred*, not derived from
> anything in the repo — if the user prefers a different floor, the assertion is
> a one-line change.

Note the exempt kinds: `backdrop`, `label`, `bar`, `panel` are not click
targets (`widgets.submit_panel`'s docstring, `widgets.py:182`: *"Panels are not
click targets — no hit-test wiring"*), so the check must filter on
`kind == "button"` from the ids **pair**, never on the widget's class.

### (d) Spacing that was tuned at 2×

The residual class, and the only genuinely un-automatable one: gaps, paddings
and margins that read fine with 2× of air and are cramped at 1×.
`pause.py:33` `_GAP = 12 → 6`; `main_menu.py:76` `_GAP = 8 → 4` (four logical
pixels between menu rows); `hud.py:81` `_ICON_GAP = 4` (already 640-scale — if
UR-2 halved this to 2 it is a conversion-rule error, not a taste call);
`highscores.py:71` `_BOTTOM_PAD = 24`; `levelup.py:82`'s `_GAP` between option
boxes. Judge by eye in §4, screen by screen.

### The standing open item this phase is expected to answer

Plan §5 lines 245-247: *"**Fonts may need re-tuning after all.** The plan
asserts the 7 presets are already 640-scale and should be left alone. If UR-5
shows they were tuned for the *stretched* look rather than the prototype's, the
fix is a `fonts.json` edit through the editor's Theme panel — data, not code."*

UR-5 is where that assertion is either confirmed or overturned. **Do not touch
`data/ui/fonts.json` on a hunch** — only on a specific playtest observation the
user signs off on, and only through the Theme panel (see §2). A global font
bump is the single change most likely to cascade into a fresh wave of class-(b)
overflows, because nothing in `game/ui` fits text to its container.

## 2. Architecture plan — the triage protocol

There is no new architecture. UR-5's architecture *is* the decision procedure
for routing an observed defect. Run every observation through this ladder, in
order, and stop at the first match.

**Step 0 — Is it §3's deferred world zoom? Then it is NOT a UR-5 defect.**

Plan §3 (lines 72-86) and §5 (lines 228-230) are explicit: flipping to 640×360
at `geometry.json`'s current `zoom_levels [1.0, 2.0, 4.0]` means the player
sees roughly a quarter of the board, and the user chose to defer the retune.
Plan line 81: *"UR-2's playtest will show a correct-looking UI over a too-close
world."* Plan line 159: *"Expect the world to look too close — that is §3, not
a bug in this phase."*

So: **the world being too close, the camera clamping sooner, tiles looking
huge, or "I can't see the base and the spawn at once" are all EXPECTED and
MUST NOT be fixed here.** They belong to a future plan covering
`data/geometry.json`'s `zoom_levels`, the camera clamp and
`visible_tile_window`'s culling margins (§5 line 230). Record them in the
report as confirmations of the known deferral. Editing `data/geometry.json` is
explicitly out of file scope (§3 below).

The line to draw: if the defect is about **UI chrome drawn in HUD space**, it
is UR-5. If it is about **the world seen through the camera**, it is deferred.
World-anchored HUD overlays (`effects.py`'s HP bars, charge bars, boss bar;
`widgets.submit_tile_diamond*`) sit on the boundary — a bar that is the wrong
*size* is UR-5 (it is a fixed screen-pixel size, `game/ui/CLAUDE.md`'s overhead
HP-bars section); a bar in the wrong *place* because the tile is drawn huge is
deferred.

**Step 1 — Is it a conversion-rule misclassification? Then it is a CODE fix.**

Symptom: a constant landed in the wrong bucket of plan §2 (lines 62-67) —
either a 640-scale constant got halved a second time (the bug the plan exists
to remove) or a 1280-scale constant was left doubled. Fix it in `game/ui/*.py`
at the constant's definition site, never at the use site, and never by
introducing a scale factor. **State which bucket you moved it to and why, in
the same commit message** — the bucket call is the whole content of the change.

Sanity rule for the "already 640-scale" bucket, from the plan's own examples:
font sizes, the 18×18 HUD icons (`hud.py:80`, whose comment *"fits the ~16-20px
HUD rows without crowding the text"* is itself the tell), hairline widths,
`border_radius`, and the fixed screen-pixel HP/charge-bar sizes in
`effects.py:182-203`.

**Step 2 — Is the *default* geometry right but a committed override wrong?
Then it is a DATA fix.**

Three files carry hardcoded rects (plan lines 45-47): `data/ui/screens/hud.json`
(4), `settings.json` (5), `main_menu.json` (3) — **verified** by reading; the
counts still hold. An override wins because `layout()` calls
`skinning.apply(...)` last (`game/ui/CLAUDE.md`, UI screen customization). So a
screen that looks wrong *only* where an override exists is a data fix.

- Edit those overrides **through the editor's screen mode** where practical
  (`editor/panels/viewport.py` — UR-3's territory) rather than by hand; the
  design pillar is "humans never hand-edit `data/` JSON, agents may, but only
  schema-valid writes".
- `data/ui/fonts.json` changes go through **the editor's Theme panel**, per §5
  line 247. Any font change is a user-approved change, never an agent judgement
  call.
- **`data/ui/screen_defaults.json` is generated — never hand-edit it.** After
  any code-side geometry change, regenerate with
  `py tools/export_ui_layouts.py` (plan lines 143-145; the exporter is
  deterministic, so a re-run with no change is byte-identical) and re-pin the
  goldens that move.

**Step 3 — Is it a re-pin, not a fix?**

If a moved rect is *correct*, the failing artifact is the pin, not the code:
`test_ui_skinning.py`'s golden baseline and `data/ui/screen_defaults.json`.
Plan §5 lines 240-243: **re-pin, do not delete** — the golden is the only thing
that catches an accidental re-scale later. Re-pin by regenerating, then read
the diff and confirm *only the screens you intended* moved; a screen you did
not touch showing a byte diff means you changed something shared.

**Step 4 — Nothing else.** Anything not matched by Steps 1-3 (engine render
behaviour, editor preview parity, asset frame sizes, `SCALED` on a
non-integer-multiple monitor) is another phase's or another plan's. Report it;
do not fix it.

## 3. File scope + shared-file contract

Deliberately open, because the phase is defined by what the playtest finds —
but bounded:

**In bounds**
- `game/ui/**` — layout constants, spacing, container sizes, label handling.
- `data/ui/**` — the 12 committed rect overrides in
  `screens/{hud,settings,main_menu}.json`; `fonts.json` **only** on a
  user-signed-off observation and **only** via the Theme panel;
  `screen_defaults.json` **only** by re-running the exporter.
- `tools/tests/test_*.py` — re-pins for anything that moves, plus at most the
  two small mechanical checks from §1 (button min-size; static-label fit).
  Bare minimum: no new coverage beyond that (plan line 219).
- `game/ui/CLAUDE.md` — only if a UI convention actually changed.

**Explicitly out of bounds**
- `data/geometry.json` — §3's deferred zoom. Touching it silently converts this
  phase into the follow-up plan and hides the deferral the user chose.
- `engine/**` — the layering rule (`game/ui` is pygame-free and consumes
  `engine.render` only). A defect that genuinely needs an engine change is a
  cross-package task: **report it, do not do it**.
- `editor/**` — UR-3 owns editor preview parity. If the preview disagrees with
  the game after a UR-5 fix, that is a UR-3 follow-up, reported not fixed.
- `data/slots.json`, `data/sprites/**` — UR-4 owns art frame sizes.
- Root `PLAN.md` — generated mirror; edit `planning/UiResolutionPLAN.md` and
  re-run `/setcurrentplan`.

**Shared-file contract.** UR-5 runs *after* UR-2/3/4, so it does not contend
with a live sibling phase. The two files that multiple phases have already
written and that this phase must therefore treat carefully:

- `data/ui/screen_defaults.json` — **only ever written by
  `py tools/export_ui_layouts.py`.** Conflicts resolve by re-running the
  exporter, never by hand (plan lines 248-249).
- `tools/tests/test_ui_skinning.py` — UR-2 already re-pinned its golden
  baseline. UR-5 re-pins **only the screens whose geometry it changed**; every
  other screen's entry must stay byte-identical, and that containment is itself
  the evidence the fix was local (the precedent is `game/ui/CLAUDE.md`'s
  player-identity note: *"Only `main_menu` moved; every other screen's entry is
  byte-identical, which is what says the change was contained"*).

Every fix is one constant, one bucket decision, one commit line saying which
bucket and why.

### The live playtest script — the phase's real deliverable

Run `py game/main.py` on a **1280×720 or 1920×1080** window first (an exact
integer `SCALED` multiple — the reference case). Run it a second time on a
non-integer size such as 1366×768 only for step 12.

Throughout, ignore one thing on purpose: **the world will look too close.**
That is `planning/UiResolutionPLAN.md` §3, deferred by the user. Do not report
it as a defect; just confirm you saw it.

1. **Main menu.** Every row's label sits fully inside its button with visible
   margin on both sides — `START NEW GAME` and `HIGH SCORES` are the tightest.
   Title and subtitle are legible and not colliding with the top row. The rows
   are separated, not touching. The `SET` gear beside `PLAY DEBUG` is big
   enough to hit on the first try — click it three times without missing.
2. **Play Debug settings modal** (the gear). The `< value >` cycler arrows are
   clickable; the four ON/OFF toggles read as distinct rows; BACK closes it.
   Then confirm a click *outside* the modal does not start a run.
3. **High scores.** Rows do not overlap each other; the header sits clear of
   the first row; the columns (name / skill / round / built / kills) do not
   run into one another and long names do not spill into the next column.
   Scroll the wheel both ways: the header stays pinned, rows clamp at both
   ends, and the scroll direction feels right (down = down the list).
4. **Settings.** All three toggle buttons hit on the first click. The
   display-mode `<` / `>` arrows hit on the first click. BACK is reachable and
   not clipped by the panel bottom. Switch display mode once and back — the
   layout must survive the round trip unchanged.
5. **Credits.** No line overlaps its neighbour; the block is vertically
   centred-ish and does not run off the bottom.
6. **Add a name.** Type a 20-character name: it stays inside the field and does
   not overhang. ADD NAME and BACK do not overlap.
7. **Start a run — HUD, idle.** Love panel and readout panel below it: numbers
   inside their pills, pills not overlapping, the love icon aligned with its
   number. XP bar and `LVL N` legible. Phase banner centred and not clipped.
   Round label reads `Tutorial` (round 0) or `ROUND n` and fits its pill.
8. **HUD controls.** Click `PAUSE` (top right), the three speed pills and the
   `DRAG SEL` toggle — **each on the first attempt, cursor placed centrally,
   then again with the cursor near each button's edge**. Any button that needs
   a second try, or whose hover highlight flickers as you cross it slowly, is a
   class-(c) defect: name the button. Then confirm the gold "active" rim on the
   selected speed and on `DRAG SEL` is still visible at this size.
9. **Pause screen.** The four rows: labels inside their buttons, gaps between
   rows visible, the panel not swallowing the bottom row. Resume.
10. **Building panel — every mode.** Click a locked tile (unlock), an empty
    buildable tile (construct card list), then place a building and click it
    (upgrade). Check: card labels and prices fit their cards; the stat rows do
    not overlap; the `Terrain: <Label>` badge fits; the Range/Level rows are
    legible. Hover a card and a terrain badge — the **tooltip** must appear
    fully on screen; repeat with a tile near the **right and bottom screen
    edges** (that is where a self-sizing tooltip now runs off).
11. **Construct preview + rename.** Open the construct preview: the name field
    holds a long typed name without overhanging, the ⚄ dice button is clickable,
    CONFIRM/CANCEL do not overlap and both hit first-try. Then place, reopen the
    building, and use the upgrade panel's rename row for the same checks.
    Then use MOVE: the instruction card text fits, and the MovePreview's
    Cost/Time/destination lines do not collide.
12. **Level-up modal.** End turns until it fires (or Ctrl+L → LEVEL UP). Each
    option box: the explanation text is wrapped inside the box with no word
    overhanging the edge (this is `wrap_text`'s known non-breaking-word case),
    the boxes are separated, and clicking each box's centre and near-edge
    registers.
13. **Combat frame.** Let a wave in. Check the overhead HP bars sit above their
    sprites and are still readable at this size; the lightning readout
    (bottom-left, ENEMY phase) and its cursor-attached progress bar are legible;
    floaters (income/XP) do not stack into an unreadable smear; the game log
    lines (bottom-left, above the phase banner) do not overlap each other.
14. **Boss / game-over / cheat menu.** Ctrl+L: the cheat menu rows and the
    round entry field fit and are clickable. Then reach a boss cutscene (or
    `goto_round`): the two option boxes' descriptions fit inside them.
    Finally let the run end: the game-over readouts fit and MAIN MENU is
    clickable.
15. **The non-integer-multiple pass.** Reopen at 1366×768 and repeat steps 8
    and 10's edge-click checks only. Any target that becomes unreliable *here
    but not at 1280×720* is `planning/UiResolutionPLAN.md` §5's known `SCALED`
    caveat (lines 236-239) — **note it in the report, do not fix it in UR-5.**

**Sign-off.** The user states, per screen or in one line for all fifteen steps,
that the UI reads correctly. Only then is UR-5 closed. A phase report must
list, separately: (i) defects found and fixed with their triage step, (ii)
defects found and deliberately deferred with their owning plan/phase, and
(iii) the fonts.json verdict — were the 7 presets right at 640-scale after all,
or does §5's open item need to become a real change?
